## 1. 产品背景（引用对齐结论，勿重复推导）

### 1.1 不变的产品约束

Kronos 是本地优先、单用户的加密货币策略研究助手。先服务 owner；只有 owner 的真实使用证明价值闭环，才讨论开放。第一层价值是“我的策略在什么条件下值得继续、不值得继续，为什么”；因子发现和平台化能力在第二层。

交互以对话为主，Web 承载结论、证据、任务状态及未来必要的授权界面。CLI 仅是工具和自动化接口，不能成为获得判断结果、重试失败或调整策略的唯一方式。

终局允许研究、观察、执行贯通，但当前交易环境上限是 Binance testnet。公开主网行情的只读获取与实盘交易权限必须分离；不因读取主网历史行情而获得任何主网下单能力。研究自主边界可以宽，但必须有预算、可证伪条件、去重、终态和每轮产出。实盘另设显式人工闸门，不承诺收益。与其他项目无产品关联。

### 1.3 回测接线：已证实的问题与推导风险

**F-01：R-breaker 名称下还没有完整的交易对象。** 当前 `RBreakerFactor` 输出的是 `(close - pivot) / (ATR × volatility_multiplier)`；突破价位被计算，但没有形成完整入场、退出和持仓状态机。配置没有定义资本、仓位、会话结束、成交或风险规则。它可以是研究特征，却还不能独立回答策略的净收益。[K05][K06]

**F-02：排名分配会改变策略含义。** `build_target_weights` 的 long-only 按排名选取，并不因为信号为负或为零而自动空仓。对于单币种输入，这可能退化成持续持有；对于三币种输入，测试的是相对排序而不是三个独立的 R-breaker 策略。这是接口语义问题，不是一次参数映射能解决的问题。[K09]

**D-01：原参数网格可能产生“伪稳健性”。** 若所有信号统一除以同一个正的倍数，横截面排名不变，因此倍率变化可能完全不改变交易。不能把这样的相同结果解释为策略对参数稳健；系统必须报告“此参数在当前执行语义下不影响决策”或“此样本没有激活该参数”。这个结论是由当前公式和排名逻辑直接推导的，不是本次实测收益。[K05][K09]

**F-03：指标字段名称和交易者语义不一致。** 当前 `win_rate` 来自收益序列中正收益 bar 的占比，`profit_factor` 也是基于 bar 的正负收益汇总，`trade_count` 不能直接作为闭合往返交易数。结论卡所需“交易胜率、平均盈利／平均亏损、持仓时长”必须从闭合交易账本产生，不能直接改标签。[K10]

**D-02：时序、归因和性能需要针对性证明。** 当前引擎在本 bar 收益计入后再应用排程目标；这与“收盘发信号、下一根开盘成交”的常见产品理解不是同一个事件顺序。持仓快照使用调仓后的权重，而权益收益使用此前权重，归因可能不一致。排程逐组从时间轴头部寻找下一时间点，存在 `O(S×T)` 扫描风险；1m 长历史不能用小 fixture 的速度推断。这些项目需要金标准测试和性能测量，本文不把未测量的影响量写成已确认的数值故障。[K08]

**F-04：当前 Freqtrade 桥不是已完成的外部验证。** 它接受调用方提供的外部结果，生成配置／命令并比较，但没有实际启动 Freqtrade；缺少 lookahead 输出时默认通过。集成测试还直接复制 Kronos 自身净值作为 Freqtrade 对照。因此“桥测试通过”和“两套实现实际一致”是两回事。[K11][K25]

**F-05：策略身份可能在旧研究映射中丢失。** `candidate_spec_from_strategy_config` 的候选对象没有完整携带策略参数与 timeframe。新版不能依赖名称或候选 ID 再找回默认实现；必须传递完整不可变的 `StrategySpec`，并检验每一个参数确实进入执行。[K06]

**F-06：测试网环境还存在需要核验的接口漂移。** 基线代码写死 `https://testnet.binancefuture.com`，而本次读取的 Binance 官方 USD-M 文档列出的 testnet REST 地址是 `https://demo-fapi.binance.com`。这证明配置与当前文档不同，不证明旧地址已经失效；本次未进行连通性或凭证验证。后续启用 testnet 前须核对环境、端点和能力白名单，不能把“修改 URL”当作可绕过环境授权的通用设置。[K21][M18]

**结论：**“接到配置能跑”的演示适配不是可信产品化。真正工作量在策略协议、交易账本、成本与资金费率、PIT、独立正确性校验和性能修正；评估见 §3.3、§10.3。

### 1.4 Web 与 Agent 骨架的复用判断

Web 不是“什么都没有”：已有 Next/React、Radix、TanStack Query 和图表基础。问题是主工作流围绕候选池、记忆、报告、审批和运行面板组织，首页没有策略对话路径；多个面板数据被同时查询，单个边缘接口失败也会影响首页总体健康提示。未运行浏览器，因此不把视觉审美或响应速度评为实测结论；但信息架构错位已可从代码确认。[K22][K23]

Agent 的复用应按能力分层，而不是报一个没有依据的“复用率 80%”：

| 组件 | 复用判断 | 必须补足／替换的部分 |
|---|---|---|
| 事件、错误、产物引用类型 | 高复用价值 | 稳定序号、关联 ID、事务提交、脱敏和版本迁移 |
| 工具注册与执行记录 | 中高复用价值 | 严格输入输出校验；工具名绑定 handler；能力权限、超时、预算和幂等 |
| Supervisor | 状态投影可复用，不能直接当 worker | 当前 start/stop 主要改变状态；需真实任务执行、取消确认、租约和进程恢复 |
| Candidate 状态机、失败收敛 helper | 概念可复用 | 区分策略、修订、研究轮次；把终止规则放进真实执行边界，不能只保留辅助函数 |
| `run_agent_once` | 报表外壳可参考，主流程不复用 | 目前主要消费已有证据并 propose/conclude，不执行提议实验；重用 run ID 会清理旧产物 |
| `AgentConsole` | 环境提示和局部服务调用可提取 | 不迁移 CLI 菜单／REPL 到 HTTP；会话和用户意图独立建模 |
| 模型角色、秘密存储 | 通过接口复用 | 供应商能力测试、调用预算、输出截断、失败降级；开发记忆不作为交易事实来源 |

证据来自上述实现，不等于已证明所有旧调用方都执行了这些安全约束。[K16][K17][K18][K19][K20]

## 2. 版本目标（2026-09-27 与 owner 两轮对齐后确定）

### 2.1 唯一产品目标

**owner 在 Web 里提出自己的 R-breaker 策略问题，不准备 CSV、不运行研究命令，获得一份能解释、能追溯、能比较、允许拒判的策略结论；随后用一句话改变一个参数，理解结论为什么变化，并形成一个明确的下一步决定。**

本版本不是预测下一根 K 线，也不是证明能赚钱。它降低 owner 做错误判断、在错误参数上继续投入或误把基础设施成功当作策略成功的风险。

### 2.2 价值时刻

主路径为：“这套 R-breaker 值不值得继续？”→ 展示所理解的策略修订和假设 → 自动准备三币种数据 → 可见、可取消的执行 → 结论卡 → “为什么不如持有？”的证据问答 → “把倍数改成 2.0” → 新旧结论与参数差异 → owner 决定继续观察、具体改造、放弃当前修订或先补证据。

“数据不足，暂不能判断”可以是正确且有价值的结果，但必须说明缺少什么、已经完成什么、如何在 Web 内继续。只有一句免责声明不算闭环。

### 2.3 交付原则与反目标

用户无需理解 FactorRegistry、实验目录、候选晋升或 CLI 语法。核心数字无论 LLM 是否可用都由确定性程序提供；自然语言解释失败不应抹掉已完成的计算。界面不能以“Agent 已完成”替代结果，不能以绿色成功状态暗示策略盈利或可以交易。

成功不以新增因子数、Agent 角色数、工具数量、报告篇幅或测试总数衡量。首版没有实盘收益目标；策略产生负面结论也可以完成产品验收。

## 3. Agent 架构市场调研（2026-09-27）

### 3.1 调研对象概览

### 3.2 各方案要点与原调研结论的修正

#### RD-Agent：可拆的是研究协议，不是整个 Qlib 世界

源码显示：Hypothesis 提供假设和依据；Feedback 区分运行异常、是否接受、观察、评价与下一假设；Trace 记录实验与反馈以及父节点关系。prompt 构造把场景、输出格式、用户约束、历史反馈和 RAG 分开，实验转换还有显式重试。这些结构都可以映射成 Kronos 的研究任务和证据引用。[M03][M04][M14]

推荐借用四个概念：**可证伪假设、实验协议、观察结果、修订谱系**。不复制其默认数据、评价目标、研究角色或生成代码权限。不把“有 loop 上限”夸大成完整治理，也不把“未默认强制预算”误写为没有任何上限。Kronos 需要额外把嵌套重试、模型调用与候选分支都计入同一预算。[M02][M04]

源码级拆借已经足够支持上述结论；量化场景整体迁移收益和实际成本仍需单独原型，不能由作者某个实验的低成本宣传外推。

#### TradingAgents：反思要绑定事后证据，也要防止事后知识倒灌

当前 `TradingMemoryLog` 先写 pending decision，之后补 raw return、alpha、holding days、reflection 与 resolution date；上下文读取可以按 `as_of` 排除尚未揭晓的结果，并区分同标的历史和跨标的经验。它也有按标的／日期去重以及原子替换更新。[M06]

Kronos 应采用其时间边界思想，但不复制 Markdown 文本解析作为权威数据库，也不能仅用“标的＋日期”去重，因为不同策略参数是不同实验。建议研究事实存入结构化记录，Markdown 只是导出；反思必须引用已完成运行，不允许 LLM 自己描述“上次赚了”。是否运行多角色辩论，要看它能否在同等预算下改善 owner 判断，而不是看对话是否更热闹。

#### Freqtrade/FreqAI：比原规划认为的更有用，但不是正确性豁免

FreqAI 不是 LLM 研究员，但确有训练、自动重训练和历史回放能力，所以“完全没有研究能力”不准确；但它确实不是假设驱动的 LLM 研究员。更直接的首版价值在 Freqtrade 的策略回测与交易账本。[M07]

必须正视默认假设：官方文档说明 bar 回测有入场开盘价、价格范围内完全成交、默认无滑点等假设。lookahead 与 recursive analysis 是有针对性的检查，不是对所有前视偏差和真实执行的数学保证。接入时需固定策略、完整历史输入、版本、配置及缓存边界，不能把外部结果的一个 `passed` 字符串当作背书。[M08][M15][M16]

永续适配还有明确的额外核对项：合约命名、mark price 与资金费率数据不能只凭普通 OHLCV 映射带过。官方文档明确说明缺失费率以假设值代替会使历史结果不准确，也说明强平费未完整计入；Kronos 不应为了让回测跑起来而把这些缺项静默设零。[M19]

Kronos 为 MIT，Freqtrade 仓库许可证为 GPLv3。采用固定版本的独立进程是降低耦合的工程方案，**不能据此自行断言已经解决许可证问题**；未来分发方式、修改和组合关系必须另行核对。[K26][M13]

#### 其余候选的边界

ai-hedge-fund 值得借鉴的是用户 mandate 和历史评估局限的显式处理，而非人格模拟。FinRobot 值得借鉴的是从计算、数据来源到交付物的完整路径，而非将股票估值报告搬进日内策略。NautilusTrader 的价值在执行语义，LangGraph 的价值在流程状态；它们都不能代替策略结论的业务规则。[M09][M10][M11][M12]

### 3.3 技术选型建议：把“自研薄层”拆成两项决策

#### A. Agent 编排：首版建议不引入通用 Agent 框架，但补齐真实可靠性

v0.5.0 的流程是有限工具集、有限轮次、明确状态的策略评估；没有任意代码生成、多研究分支竞争或跨系统长审批。建议使用 **FastAPI＋现有类型／工具接口＋SQLite 持久任务＋单 worker**。这里的“自建”只覆盖产品编排和控制面，不意味着自建全部金融计算。

LangGraph 的有限比较原型须使用同一套领域服务，测试恢复、取消、严格工具输入、LLM 超时、会话续接和预算扣减。投入上限建议为 **2–4 人日**；这是设计阶段工作量估计，不是本次已经完成的实验。只有当它明显减少可靠编排代码且不制造第二套业务真相时才采用。若采用，任务队列负责领取／资源，checkpoint 负责节点恢复，RunRecord 负责领域状态，职责不能互相覆盖；整体适配另计约 **4–8 人日**。框架本身仍不负责订单幂等或 token 预算。[M12]

#### B. 交易回测：建议优先验证 Freqtrade 适配，而不是默认继续改排名引擎

**建议基线：Kronos 自有 StrategySpec／数据快照／结论契约；交易回测先以固定版本 Freqtrade 隔离运行器验证。** 这是待 M0 证实的工程建议，不是宣称已验证兼容。若关键语义无法忠实表达，必须形成失败证据并由 owner 批准替代方案；不能为了适配第三方引擎偷偷改变策略。

| 路径 | 工作范围 | 粗估独立工作量 | 核心风险／采用条件 |
|---|---|---:|---|
| 直接把 score 送入现有排名引擎 | 改配置、改入口、拼 JSON | 低，但不构成合格交付 | 策略含义改变；明确拒绝 |
| 扩展现有库为单策略、仓位／订单驱动回测 | 新交易适配、账本、时序、成本与资金费率、指标、排程性能 | 12–22 人日 | 不能继续通过排名接口绕行；需要独立金标准与外部对照 |
| Freqtrade 作为主回测运行器 | 冻结版本、数据映射、策略适配、成本／资金费率核对、结果归一化与隔离运行 | 10–18 人日 | 需通过语义、安装、许可证及性能门；不能使用默认无滑点结果直接下结论 |
| 全面迁移 NautilusTrader | 市场对象、数据、订单、账户和策略模型迁移 | 20–35 人日起 | 更适合执行一致性需求上升后的评估；首版收益不足以证明全面迁移合理 |

以上是基于已读代码的范围估计，假设熟悉 Python 的工程师、仅一个策略和三币种、没有 tick／订单簿仿真；未做原型，可信度中低，不能当作排期承诺。共同的数据、结论、Web、任务治理工作另列 §10.3，不重复相加。

**M0 选择门：**两种认真候选须使用相同策略协议和手算数据。比较单边交易、平仓后反向、资金费率时点、空仓、缺 bar、费用、日切、参数变化和重启产物。先判语义正确，再比较一次安装是否适合 owner、资源开销和后续维护。不得用各自不同的成交规则比 Sharpe 决定胜负。

## 4. Scope（随本规划冻结的功能边界与技术方向）

### 4.1 本版本必须交付的闭环

| 交付项 | 包含 | 不得缩水为 |
|---|---|---|
| 对话入口 | 真实问答、合法调参重跑、上下文中的当前策略与当前结论 | CLI 菜单的 Web 包装、只有固定按钮的演示 |
| 策略对象 | 一种明确版本的 R-breaker 交易协议，参数修订、完整执行假设 | 只有策略名称和因子数值 |
| 数据准备 | 三币种 90 天 1m、必需资金费率、额外预热、质量检查、冻结快照 | 拉到若干文件、只检查最早和最晚日期 |
| 确定性评估 | 单策略经济回测、基准、成本压力、固定参数邻域、时间与币种切片 | IC 晋升、只输出收益最高的参数 |
| 结论卡 | 研究处置、证据状态、净收益与风险、局限、具体下一步 | “通过／不通过”或一大段无法核对的 LLM 文字 |
| 任务体验 | 已受理、实际执行、取消、失败原因、恢复、历史查询 | 前端转圈或 Supervisor 的状态标记 |
| 可复现产物 | 数据／配置／代码／引擎／规则版本及账本引用 | 同名文件覆盖、动态 latest 链接 |
| 首次可用性 | 本地启动入口、Web 设置模型、数据自动准备、无模型／断网的明确处理 | 要求 owner 学习研究 CLI 或手工寻找报告路径 |

### 4.2 StrategySpec：先决定“测的究竟是什么”

**发布阻塞决策：owner 必须确认 R-breaker 的具体变体。** 目前公开配置并不足以回答这个问题。本规划不把现有因子静默改名成经典策略，也不替 owner 虚构他原本想测试的规则。

推荐顺序是：优先实现 owner 实际希望判断的 R-breaker 规则；将这些规则写成可执行行为表和手算案例。如果 owner 明确选择先判断当前实现的阈值变体，则卡片必须标明“Kronos pivot/ATR 阈值变体”，不能笼统宣称已经验证经典 R-breaker。二者只能选一个作为本版本模板，不扩展为两个产品模板。

为让此决策可落地，而非继续抽象讨论，M0 须完成以下协议：

| 协议字段 | 必须明确的内容 | 本规划建议的公共默认边界 |
|---|---|---|
| 身份 | template、variant、规则版本、参数、父修订 | 每次调参产生新修订，不改写历史 |
| 市场 | venue、USD-M perpetual、symbol、结算资产 | BTCUSDT 为初始主样本；ETHUSDT、SOLUSDT 为相同规则对照，不自动拼成组合 |
| 信息集 | 前一完整交易日 H/L/C，ATR 公式、周期和预热 | UTC 日界；指标只使用在决策时已经完整可知的数据 |
| 入场 | 哪个价格穿越哪个阈值、是否需前一 bar 确认、方向权限 | 用明确布尔条件与事件，不用“信号越大越可以买”代替 |
| 出场 | 平仓、反转、会话结束、止损／止盈、冲突优先级 | 每个分支有示例；不支持的规则明确拒绝，不近似偷换 |
| 仓位 | 初始资本、数量／权益关系、杠杆、增减仓和取整 | 三个独立单币种账户做对照；默认不叠仓，不自动构造多币种资金分配 |
| 成交 | signal_time、available_at、order_time、fill_time、价格与延迟 | 收盘后形成信号，只允许其后可交易的基础 1m 价格事件成交 |
| 边界 | 开头预热、末端未平仓、日切、缺数据、费用不足 | 未平仓单列；不得伪造“已闭合盈利交易” |

**可供 owner 选择的最小变体示例，不是已授权的策略定义：**保留现有标准化分数 `q`，空仓时 `q≥1` 开多、`q≤−1` 开空；多头 `q≤0` 退出，空头 `q≥0` 退出；UTC 会话结束优先退出；不在同一价格事件反手；数量在开仓时确定，持仓中不按每根 bar 重新等权。此时 `volatility_multiplier` 通过阈值真正影响交易。若选这一方案，产品必须显式标注它是当前代码的可交易化变体。若 owner 要其他 R-breaker 规则，则用其规则替换本示例并重做金标准，不能因“方便接引擎”保留示例。

配置契约使用严格 schema，拒绝未知字段；至少包含 `strategy_revision_id / template_version / variant / symbols / signal_timeframe / execution_timeframe / params / position_policy / fill_policy / cost_policy_id`。参数的意义必须可解释：ATR 周期究竟是几根 bar，不得在从 15m 换到 1h 后还称为同样的时间长度。

“本版本不注册策略”是指不自动发布进 FactorRegistry、候选晋升或执行系统；**会话修订和运行配置必须持久化**，否则无法追溯和比较。

### 4.3 数据自动拉齐与快照契约

默认目标是 BTCUSDT、ETHUSDT、SOLUSDT 的 **90 个完整 UTC 日** 1m 行情，另加所选规则需要的预热和前日统计数据。若 owner 改用滚动到最近完整 bar 的窗口，应作为显式策略评估设置，不在同一会话悄悄移动截止点。

首次提问先创建任务，随后计算各币种的所需区间与已有覆盖。已有库按最大时间增量同步，不能补足所有历史缺口，因此新增 `DataReadinessPlan`：按区间检查首尾、内部缺失、重复、异常、完整聚合桶及来源，再仅补缺口。三币种可以复用缓存和已完成下载，但限速预算应按交易所入口共享，不能让并行 worker 各自认为没有超额。[K14][K15]

R-breaker 只拉取真正需要的数据：行情、资金费率及计算成本所需的结算参考；不因为旧 `sync_all` 习惯性拉 OI，就把 90 天 OI 变成首问阻塞。OI 若非规则输入，本版本不需要。若选 Freqtrade，还要验证 `BTCUSDT → BTC/USDT:USDT` 等合约映射，以及引擎需要的 mark price 数据；必要时新增只读 mark 数据适配，不能假定已有文件天然满足其永续输入协议。[M19]

数据质量门要求：

| 检查 | 规则 |
|---|---|
| K 线完整性 | 只用闭合 bar；聚合桶必须具有所需的完整基础 bar 集合。缺失先修复，修不了明确阻塞该样本，不默认填平价格 |
| 时间可知性 | 区分 bar 起点、收盘可知时间、抓取时间；信号只能引用当时可知数据 |
| 历史模拟局限 | 今天下载的历史数据不等于当年实际接收的数据；历史 available_at 若按规则重建，必须标记为“模拟可知时间” |
| 资金费率 | 按真实结算事件处理，不能 forward-fill 后每根 bar 重复收费；支付方向和结算时点由持仓账本决定 |
| 来源 | 合成／fixture 与真实行情分命名空间；全样本和 manifest 校验，不能只看第一个币种第一行 |
| 快照 | 保存 venue、合约、区间、schema、来源、抓取信息、数据校验结果和内容哈希；重采样不丢来源关联 |
| 数据不足 | 缺一项不能静默当零成本或自动退回合成数据；给出可重试任务和部分产物 |

三币种 90 天 1m 的基础行情是 `3×90×24×60=388,800` 根，另加预热。规模本身不需要分布式数据平台；真正风险在现有算法、下载容错和语义正确性。

主币种准备好后可以提前显示“部分结果，尚未完成对照”，但不得把三币种任务标成全部完成。数据完全失效时，禁止给出正式策略处置；失败也要留下质量报告。最后形成不可变 `DataSnapshotManifest`，以后调参默认复用同一截止点和同一数据快照；“更新数据再评估”才创建新快照。

### 4.4 交易回测与指标协议

应用层依赖 `StrategyBacktestAdapter`，不依赖特定第三方内部对象。输入是已冻结的策略协议和数据快照，输出是规范化订单／成交／资金费率／仓位／权益账本。当前排名引擎保留自己的研究用途，不通过重命名输出成为新适配器。

**时间顺序是验收对象。** 每笔交易需要回答：使用哪根已完成 K 线、何时可知、何时下达模拟意图、使用哪个之后的价格事件成交。零延迟只能作为明确研究假设；至少给一个基础 bar 延迟的压力情景。若目标策略使用 intrabar 触发，必须定义基础 1m 内部无法观察的路径假设，或者明确该版本不支持该变体，不能按“看见最高价就按最好价格成交”处理。

**成本与账户规则：**费用按每次开平仓、方向和名义金额计入；反转按相应的平仓＋开仓处理。滑点、资金费率、数量精度、最小下单约束、资金不足和保证金模型必须进入假设清单。初始费用可以是 owner 批准的研究假设，不能冒充他的实际手续费等级。缺少完整历史保证金／强平模型时，必须标示模型边界并阻断“实盘就绪”类结论；不能以默认 1 倍杠杆宣称没有强平风险。

| 指标 | 统一口径 |
|---|---|
| 净收益 | 权益期末／期初−1，含已声明的手续费、滑点、资金费率；末端未平仓估值与假设清算成本分列 |
| 最大回撤 | 从包含初始资本点的完整权益序列计算，返回峰、谷、期间和绝对／比例值 |
| 交易数 | 完整闭合的往返交易数；订单、成交笔数、调仓次数另列 |
| 胜率 | 扣除分摊成本后的盈利闭合交易／全部闭合交易；平局明确计入分母 |
| 盈亏比 | 平均盈利交易收益／平均亏损交易损失绝对值；不得以 profit factor 替代 |
| Profit factor | 闭合交易盈利总额／亏损总额绝对值，单独命名 |
| 持仓时长 | 来自真实开平仓时间差；不是缺字段时填零 |
| 暴露与换手 | 暴露按同一时间点汇总；交易换手由成交名义金额和权益口径计算 |
| Sharpe 等 | 作为辅助，不作首屏核心通过标准；使用明确频率，禁止无解释地把短历史年化成承诺 |
| 零分母／无交易 | `null`＋原因，不把 undefined 变成 0 或 JSON 的 Infinity |

主对照是同币种、同时间、同资本和可比成本下的持有策略，并同时显示现金空仓参考。对于永续策略，必须说明持有对照是否也计资金费率。低收益、低回撤与高收益、高回撤是取舍，不允许只因跑输持有就自动判坏，也不允许只因绝对收益为正就判好。

按币种单独报告同一规则的结果；本版本不产生综合组合成绩。收益归因必须能与权益变化对账，包含费用和资金费率；无法核对时拒绝生成正式结论。

### 4.5 参数邻域、时间切片与证据边界

默认只做**预先定义的小邻域诊断**，不做“帮你自动找最好参数”。建议中心点加 ATR 周期和 multiplier 的两侧邻点，最多 3×3 组合；实际范围必须与 owner 确认的参数语义和有效边界一致。截断、重复参数点和未激活参数须显式说明。

初始 90 天可采用前 60 天诊断、后 30 天留出核对；这个切分是建议的研究协议，不是声称 30 天足以证明有效。中心策略的全 90 天表现可以呈现，但必须与开发段、留出段分开；邻域主要在开发段评价，不反复挑选留出收益最高者。

每次看过留出结果后再调参，都记录 `holdout_exposed=true` 和尝试次数。后续重跑仍有描述性价值，但不能继续把同一段称作“全新样本外证明”。本版本不强行扩展默认 90 天要求；更长历史或未来观察是补证路径。

市场状态划分必须使用预先固定、仅依赖过去信息的规则，例如滞后趋势／波动条件；不得事后按盈亏好坏定义“适合的市场”。同时显示各切片样本数和交易数。三币种对照不能未经检验就当成三个独立实验，邻近参数高度相似也不能当成多个独立成功证据。

成本压力至少包括原假设和更不利的一档；如费用改变仓位规模或交易路径，应重新执行，而不是把同一净值机械减一个常数。证据不确定性优先用分段表现、样本计数和集中度表达；实现区间估计时，应采用尊重时间结构的重采样并披露方法，绝不输出没有校准依据的“95% 盈利概率”。

### 4.6 结论卡：双层判断与唯一数据流

**第一层是证据状态：**`valid / limited / insufficient / invalid`。**第二层是研究处置：**`observe / redesign / retire_current_revision / null`。保留原三种处置含义，但增加明确拒判；`observe` 只表示值得进一步观察，绝不是订单或实盘许可。

| 情况 | 卡片行为 |
|---|---|
| 来源不明、账本不守恒、数据不完整、策略语义未确认 | `invalid` 或 `insufficient`；处置为空；列阻塞项与已有产物 |
| 无交易或交易太少 | 显示事实和样本不足，禁止由 0 胜率推导失败或由无亏损推导稳健 |
| 毛收益尚可，但成本吞噬；参数敏感或只在少数切片成立 | 可以建议改造，指出可验证原因，不能自动启动无限搜索 |
| 当前修订违反明确风险约束，或在事先约定检验中无继续投入依据 | 可以放弃当前修订；不得宣布整个策略家族永久无效 |
| 有继续研究价值，但仍有有限样本与执行局限 | 观察；列出尚待满足的证据条件 |

处置规则由可版本化 `VerdictPolicy` 决定，在看到本轮结果之前冻结。最低交易样本、风险容忍和邻域一致性门槛是政策选择，不是假装存在全市场通用阈值；可暂以“30 笔闭合交易”作为工程警戒线，但只能标记不足，不能据此宣称统计充分。owner 未给个人回撤约束时，系统评价“是否值得继续研究”，不假装已评价“是否适合你的资金”。

首屏固定回答四件事：**当前研究结论、最重要证据、最大限制、下一步**。展开后包含策略修订、假设、数据区间、基准、交易级指标、成本、分币种／分状态／邻域表和完整账本。每个数字都有单位、分母、时间区间和 artifact 内字段位置。

```text
用户问题／参数变更
  → ConversationIntent（严格解析和权限检查）
  → StrategyRevision + EvaluationPlan
  → DataReadinessPlan → DataSnapshotManifest
  → StrategyBacktestAdapter → 交易／资金费率／权益账本
  → EvidenceBundle（基准、切片、成本压力、邻域）
  → VerdictPolicy → StrategyVerdict.json
  → Web 结论卡
                    ↘ LLM：只解释已存在的证据，并引用字段
```

`StrategyVerdict.json` 至少包含：schema_version、run_id、parent_run_id、strategy_revision_id、spec_hash、data_snapshot_id、engine_version、policy_version、evidence_status、disposition、reason_codes、metrics、comparisons、robustness、limitations、next_actions、artifact_refs、generated_at、execution_authority。首版 `execution_authority` 永远是 `none`。

LLM 不能重算指标、改处置标签或把缺字段补成数字。优先让解释引用 `fact_id`，数值由服务端填充；对无法支持的数字或矛盾结论丢弃解释，退回确定性模板。纯语言猜测必须标为假设，不能混入“回测已经证明”的证据段。

### 4.7 对话与 Agent 运行时接线

**同一应用服务、多个薄入口。** Web、Agent 工具、CLI JSON 都调用 Python 应用服务，不让 Web 拼接 shell 命令调用 CLI，也不在 Next 服务端复制业务规则。

```text
浏览器（对话、任务、卡片）
  → 同源 Web/API
    → ConversationService：会话、意图、当前修订、证据引用
    → EvaluationService：校验、幂等、预算、创建持久任务
      → 单计算 worker：数据准备／回测／证据／结论
        → 工具注册表中的确定性 handler
```

建议接口：`POST /api/conversations`、`POST /api/conversations/{id}/messages`、`GET /api/runs/{id}`、`GET /api/runs/{id}/events?after_seq=`、`POST /api/runs/{id}/cancel`、`GET /api/verdicts/{id}`。消息提交先持久化并返回 `202 + message_id + job_id`。意图解析与证据问答使用 API 进程内受限的异步 I/O 执行通道；数据准备和回测交给独立计算 worker，不让网络请求等待整个回测。两条通道共享持久任务、预算与事件协议；同一会话的修订写入串行化。计算期间仍可解释已完成的卡片、查看状态和取消任务，不额外建设一套 Agent 服务。

问答读取当前选定结论，不启动回测。明确的“倍数改成 2.0”“换 ETHUSDT”“改 1h”创建新修订，显示差异后直接运行；“更激进一点”或没有上下文的“换成 2”需要聚焦澄清。不支持的模板、任意 Python、网页脚本或实盘要求明确拒绝或说明版本边界。

严格工具白名单为 `ensure_data / evaluate_strategy / compare_runs / read_evidence` 等当前所需能力。工具名在服务端绑定 handler；输入输出都是严格 schema；限制 symbol、timeframe、参数范围、数据区间和产物路径。不能把“名字在白名单中”当成对任意 payload、路径或 handler 的授权。[K19]

**本版本的有界执行建议：**以下数值是初始产品保险丝，不是已经测得的最优成本。

| 资源 | 初始建议 | 执行方式 |
|---|---|---|
| LLM 调用 | 每研究轮最多 3 次，含纠错和重试；单次问答一般 1 次 | 先预留配额，再发请求；供应商不返回 usage 时保留保守估计，不算零 |
| Token | 每研究轮总输入＋输出 16k；日 100k、周 500k | 服务端累计，解释超限则用模板，不重新开启同义任务绕过 |
| 回测调用 | 每轮上限 40；计划中逐项列出中心／邻域／币种／压力／基准 | 例如 3 个中心全窗＋24 个开发段邻点＋3 个独立留出核对＋3 个成本压力＋3 个延迟压力＋3 个持有对照＝39 次；现金基准直接计算。按真实计划去重计费，超限则先缩减或显式调整预算，不能暗增搜索 |
| 并发 | 一个计算 worker，一次一个 CPU 重任务 | 三币种下载共享限速；用户问答不因 CPU 工作堵塞 API |
| 墙钟 | 初始每轮 30 分钟硬上限，可在设置中显式调整 | 含下载、等待与模型调用；到限输出预算终止与已完成产物，而非无限等待 |
| 重试 | 有限、分类、计入原预算 | 参数错误不重试；网络重试尊重退避；没有无限 LLM 自我修复 |
| 查重 | 请求幂等＋实验内容哈希 | 相同策略、数据、协议、引擎版本复用原产物；只补新的问答，不假造新实验 |

每轮至少产生一种终态产物：正式结论、证据不足说明、失败报告、取消报告或预算终止报告。LLM 不可用时允许完成确定性评估；但首版“自然语言问答可用”的最终验收仍须真实模型通过，不能用模板降级掩盖未完成功能。

### 4.8 持久任务与常驻调度器形态

**v0.5.0 建任务执行器，不建自主研究员。** 推荐本地 API 进程与一个独立计算 worker；SQLite 保存任务、会话、预算和事件。它们可由同一个本地启动器管理，但不能把 CPU 回测放在 HTTP 主事件循环里。浏览器关闭不取消研究；后端退出或进程崩溃后，任务必须可判定、可恢复。

任务至少有 `queued / running / cancel_requested / succeeded / blocked / failed / cancelled / budget_exhausted`。同时存 stage、attempt、worker_id、lease_expiry、heartbeat、fencing_token、资源消耗和错误引用。取消是请求和确认两步：停止真正的工作后才进入 cancelled，不能只改 UI 标志。过期 worker 不得再提交正式产物。

采用本地事务队列和单 worker，不引入 Redis、Kafka、Kubernetes、分布式调度或多人权限系统。原 Supervisor 可成为只读状态投影，不再与数据库各自修改一份“当前真实状态”。对纯计算和只读下载，重启可以从已提交阶段恢复；不完整临时文件须重新验证。外部操作若结果未知，不能以简单重跑代替核对。

**阶段 2 的目标进程形态：**在同一任务系统上增加独立的轻量调度进程，持有定时／事件触发规则，休眠等待时不调用 LLM。调度器只检查数据更新、任务资格、预算、冷却期和重复键，把合格研究任务交给 worker。操作系统的 launchd/systemd 等负责进程保活，不让 LLM 充当 cron。具体平台在 owner 的机器上验收，不承诺未经测试的全平台常驻。

### 4.9 产物、身份与恢复

建议新增独立的本地状态与产物目录，旧研究报告只读保留；路径可配置，不依赖仓库当前工作目录。概念上区分：会话、策略修订、任务、执行尝试、数据快照、证据包、结论。

语义缓存键由规范化策略规则、参数、市场、时间框架、数据内容哈希、成交／成本协议、引擎和指标版本组成。`run_id` 是执行身份，不能仅靠日期范围和默认配置推导；同一个请求重试也不能删除前次事件。新数据或改规则必须生成不同身份。[K08][K17]

```text
runs/<run_id>/
  request.json                 # 原请求与规范化意图
  strategy_spec.json           # 冻结的规则与参数
  evaluation_plan.json         # 时间切片、邻域、预算、判据
  data_manifest.json           # 来源、质量、内容哈希
  execution/                   # 订单、成交、费用、资金费率、仓位、权益
  evidence.json                # 指标、对照、切片及对应字段位置
  verdict.json                 # 确定性结论
  explanation.json             # 模型信息、证据引用、可选解释
  terminal_report.md           # 成功或失败／取消／预算终止产物
  manifest.json                # 最后提交的产物索引和完整性校验
```

文件先写临时位置，校验后原子替换；最终 manifest 提交后，数据库事务才发布可用结论指针。承认文件系统与数据库不是天然的一个事务：恢复逻辑须处理“文件已提交、数据库未发布”的孤立产物，并验证内容哈希，而不是默默覆盖。旧卡片永久指向原始快照，不引用会变化的 `latest`。

### 4.10 Web 骨架、启动与本地安全边界

**信息架构只保留三个主要去处：策略对话、历史／证据、设置／系统状态。** 对话页显示当前策略摘要、消息、任务进度与结论卡；历史支持从卡片回到原会话和同数据比较；设置提供模型、数据路径、预算与必要的运行诊断。

保留 Next/React、现有 UI 基础和合格的图表／设置组件。重写 WorkbenchApp 的首页组织、导航、空态和请求依赖，不要求重写所有已有组件。候选池、开发记忆、旧审批面板不再抢占主导航；旧材料／报告可放入高级只读入口，但不是首屏占位。[K22][K23]

Web 必须同时设计并测试：首次无数据、模型未配、正常问答、数据准备中、部分完成、失败、已取消、证据不足、已完成和新旧比较。活动任务可以先用增量事件轮询，不必为流式动画引入复杂 WebSocket；SSE 若采用，必须支持按事件序号恢复，不能成为唯一状态来源。

交付启动器应启动所需的前后端和 worker 并打开本地页面；不要求 owner 自己分别启动三个开发终端。允许内部用脚本或 CLI 实现启动，但首次研究、密钥配置、获取结论、重跑和故障重试都不得依赖手工 CLI。首版不引入 Electron/Tauri 作为“桌面化”附加工程。

默认仅监听 loopback，同源代理；写接口有本地会话令牌和 Origin/Host 检查，限制本地网页跨站调用。密钥仅进入后端秘密存储，不写进对话、URL、前端公开环境变量或模型 prompt。Markdown 禁止不安全 HTML；产物下载通过受限 ID 映射，不接受任意文件路径。数据源／工具参数不能被聊天内容改成任意 URL 或 shell。

“本地优先”必须诚实：数据、实验与会话默认保存在本机；调用外部 LLM 会发送经过筛选的上下文。Web 应说明发送哪些信息，并默认只发送策略摘要与必要证据，不发送 API Key、全量原始数据或开发者私人记忆。

## 7. 测试

### 7.1 测试原则

测试要证明“判断所依据的事实是什么”，不只是证明 JSON 字段存在。测试金标准不能调用被测指标函数生成预期值，也不能把被测引擎净值复制给所谓第二实现。所有 fixture 明确标注合成；可在 CI 中使用，但不能进入真实使用的经济结论。[K25]

### 7.2 确定性经济正确性

| 测试组 | 必测情景 | 验证内容 |
|---|---|---|
| 手算交易样例 | 少量 bar 的开仓、平仓、先平后反向、空仓、日切和末端持仓 | 明确每笔价格、数量、时间、费用、已实现／未实现盈亏与最终权益 |
| 资金费率 | 结算前开仓、结算后开仓、结算前平仓；多空与正负费率 | 只对结算规则规定的持仓收费／付费；没有逐 bar 重复计费或时间偷看 |
| 交易级指标 | 费用把毛盈利变净亏损、平局、零交易、全赢、全亏、未闭合交易 | 胜率分母、盈亏比、profit factor、交易计数、null 与原因均正确 |
| 权益与归因 | 初始资本点、首笔费用、最大峰谷、多个费用事件 | 回撤包含初始点；净值变化与交易、未实现损益、手续费和资金费率一致 |
| 参数传播 | 改 multiplier、ATR、symbol、timeframe | 参数进入引擎；构造样本证明规则可受影响；样本内未激活也能正确解释，不能要求每次改参必改收益 |
| 时间／PIT | 追加未来数据、改变未来价格、同日统计、聚合未完成 bar | 已发生决策不受未来输入改变；日统计仅来自前一完整日；信号不能使用未闭合 bar |
| 单币种与多币种隔离 | 交换币种顺序、只改另一个币种数据 | 独立单币种结果不互相污染；禁止误入横截面排名 |
| 故障与异常输入 | 缺 bar、负价格、重复时间、非法参数、NaN、非法成本 | 结构化失败或拒判；不能悄悄填零、跳过并给正式合格结论 |

补充两类重要测试：一是当前分数统一正比例缩放不改变排名的回归样例，防止将其误认为参数稳健性；二是固定成交路径下费用增加应使净结果不改善的性质测试。后者只在成交与数量固定的前提下成立，不能误用来否定重新计算仓位后可能改变的交易路径。

开发段／留出段交界还必须明确持仓处理：独立留出评估可带入历史指标预热，但是否带入开发段持仓必须固定并标注。主分析建议留出段从空仓开始；全 90 天连续权益另行保留，不能把两段简单拼接成一条看似连续的实盘净值。

### 7.3 引擎独立核对与数据验证

选定主回测器后，用与主实现独立的手算账本／极小参考实现核对关键路径；再对代表性的真实数据片段保存逐笔对照。另一成熟引擎的实际运行可以提供额外证据，但不能为了形式上的“双引擎”长期维护两套生产业务逻辑。

若对外标注 Freqtrade 验证，必须留存实际命令参数、版本、输入哈希、退出状态、原始结果和差异报告；检查未运行、交易太少或条件不适用时分别记录，不能概括为通过。浮点误差、成交取整和指标差异的容差须提前固定，重要离散事件必须逐笔解释，不能只要求“最终收益接近”。[M08][M15][M16]

数据测试覆盖 429／超时／断点续传／部分币种完成、坏行拒绝、目标区间首尾及中间缺口、资金费率缺失、聚合不足、来源混合、文件校验失败、预热不足。离线网络 mock 验证协议；另设只读真实 Binance 行情验收，不使用交易凭证，不下单。不同机器时区和 UI 时区不能改变 UTC 策略结果。

### 7.4 对话、任务可靠性与安全

| 层面 | 必须通过的测试 |
|---|---|
| 意图与问答 | 明确调参直接重跑；歧义聚焦追问；不支持规则不执行；追问读取当前明确的 run 而非目录中“最新”报告 |
| LLM 事实一致性 | 诱导模型捏造胜率、保证收益、忽略不足、覆盖风险结论；系统仍仅引用真实字段或明确拒答 |
| 预算 | 含重试的调用／token 限额；预算预留并发安全；供应商 usage 缺失；重启不重置账本；纯等待和确定性任务不发 LLM 请求 |
| 输入安全 | prompt 注入、任意路径、shell、越界 URL、未知工具、过长消息／输出；不能改变后端权限、执行环境或秘密边界 |
| 幂等与恢复 | 双击提交、HTTP 重试、重启、worker 失联、阶段中断、产物写完但状态未提交、旧 worker 迟到提交 |
| 取消 | 运行前、下载中、回测中和模型等待中取消；真正停止后才确认；保留已消耗预算和终止报告 |
| 模型故障 | 超时、断流、schema 错误、响应过长、凭证失效；有限纠错后降级，不丢已生成证据 |
| 执行隔离 | “直接实盘”“改成主网”“拿测试网 Key 试一下”等消息不会使首版研究工具下单；后台不因旧 paper 面板存在而自动调用交易 |
| 本地 Web | 非同源写请求被拒；密钥不出现在日志、产物、前端包和模型上下文；下载不能越过受限目录 |

对 CPU worker 和会话 I/O 分别施加压力：回测不能阻塞“查看状态、取消、解释上一张卡”的路径。不要只测请求返回了 202，而不测任务是否真正执行以及最终产物是否对应原请求。

### 7.5 浏览器与真实 owner 验收

自动化浏览器测试从空数据目录进入，覆盖设置模型、首次真实流程的受控 mock、进度、失败重试、结论展开、追问、一次参数重跑、同快照比较、刷新和重启后的恢复。另测不足证据、零交易和无模型等状态，不能只测成功卡片。

在 owner 实际桌面浏览器／窗口尺寸完成真实使用：使用真实行情与实际模型；owner 自己提出问题和至少一次参数修改，不预先背好演示话术。至少有一次后续重新打开历史、追问或比较的使用，验证可回访性。测试记录区分“模型能答”“数据可信”“owner 觉得有用”，三者不能互相代替。

### 7.6 性能与回归门

记录目标机器、引擎版本、输入规模、冷／热缓存、下载时间、计算时间、模型时间、峰值内存及产物大小。至少测三币种 90 天的默认周期、1h 重跑、完整邻域和支持范围内的最大预热；1m 若承诺作为信号周期，也必须进入性能验收，不能只因配置解析接受它就宣称支持。

建议本地受理请求在 1 秒内显示已受理、运行期间至少每 5 秒有可见的阶段或心跳更新。这是体验目标，不是已测事实；冷启动总耗时和热重跑时限在 M0 用 owner 机器测定并冻结。超过目标先暴露瓶颈与缩减非必要工作，不隐藏进度或宣称未经测量的“分钟级必达”。

回归保持 ruff、mypy、Python 测试及 Web lint/typecheck/build。新增 Web 组件与浏览器 E2E 测试不能以现有前端没有 test script 为理由省略。[K23]

当前报告基线为 618 通过、86% 覆盖率；开工后先取得同一统计口径的真实基线。建议总覆盖率不低于这条核验后的基线，不将原规划的 80% 当成主动降低标准的理由。更重要的发布门是上述关键错误分支和经济不变量均有测试；覆盖率数字不能豁免任何一个 P0。[K04]

### 8.2 “有用”如何裁决

请 owner 在不由开发者代答的情况下说明：这次测的具体规则是什么、结论依赖哪项证据、最大不确定性是什么、改参后究竟改变了什么、下一步准备做什么。若回答依赖开发者补充口头解释，卡片或对话仍未完成。

不要求 owner 接受正面结论，也不要求产生盈利；一个可信地告诉 owner“当前证据不够，不该继续加码”的结果同样可能有价值。但不能把永远返回“不知道”当成达成产品目标：在数据和协议充分的正常测试中，系统必须给出有依据的具体分析。

### 8.3 一票否决项

出现策略语义偷换、合成数据冒充真实、缺失外部检查默认为通过、卡片数字无法对账、秘密泄漏、无效取消仍伪报终止、预算绕过、未授权交易，均阻塞发布。owner 的主观满意不能豁免这些底线；反过来，工程底线通过也不能豁免 owner 对产品“不好用”的否决。

## 10. 定稿路径（剩余步骤）

### 10.1 内部里程碑：分阶段实现，单版本交付

| 里程碑 | 输出 | 出口条件 | 不允许的捷径 |
|---|---|---|---|
| M0 语义与选型门 | 唯一策略协议、手算案例、回测内核比较证据、任务／卡片契约、对话主流程草图 | owner 批准语义及有界 Web 重构；引擎语义／安装／许可核对形成 ADR | 用当前因子名代表策略；未比较就默认自研；拿草图当价值验收 |
| M1 可信的确定性纵向链路 | 配置→真实数据快照→交易账本→证据→卡片 JSON | 单主样本与关键故障先通过独立核对，再扩展相同协议到三币种和邻域 | 先用复制净值通过“交叉验证”；只校验字段、不验证经济意义 |
| M2 Web 主闭环 | 首问、进度、结论、追问、修订重跑、比较、历史／设置；持久任务与预算接通 | 从 Web 全程可达，模型解释可引用证据，重跑对应准确修订和快照 | 只在 CLI 演示；聊天和后台各自维护一套业务状态 |
| M3 可靠性与边界 | 数据／worker／模型故障、取消、重启、安全与性能测试 | §7 关键路径通过；在承诺支持的目标环境冻结体验指标 | 用线程内状态伪装恢复；超时无限重试；扩大并发掩盖算法问题 |
| M4 owner 自用与发布门 | 真实使用、回访、缺陷修正、文档和剩余风险清单 | §8 全部满足；owner 明确认为有用 | 工具层提前发版；因 CI 绿跳过 owner 否决 |

主依赖为 M0→M1→M2→M3→M4；协议冻结后，Web 基础与部分测试可以并行。M1 是内部验证点，不是对 owner 交付的独立版本。首版以可运行主线逐步替换旧路径，不批量翻修无关因子模块。

### 10.2 阶段 2–4 的路线修正

**路线顺序总体保留，但“常驻”“观察”“执行安全”的前置关系需更精确。** 首版必须有可靠长任务；常驻研究不必等全部因子基础设施完成；观察协议必须在结果出来前制定；执行安全要在任何自主 testnet 权限启用前完成，不能留到实盘阶段才补。

#### 阶段 2：有界常驻研究员，而不是定时重复写报告

常驻调度器只处理时间、数据变化、任务资格、预算与冷却。用户关闭浏览器不停止；无到期任务、无新数据或预算不足时不调用 LLM。系统休眠恢复后合并错过的触发，不把每个错过的 tick 补成一次研究。日／周预算不能因新建会话、改标题、重启或创建子任务而重置。

每个 `ResearchEpisode` 至少含 hypothesis、falsification_criteria、data_scope、protocol、parent_episode、dedupe_key、budget、stop_conditions、artifacts 和最终处置。每轮必须产生“新证据、反证、无法取得证据的原因或资源终止”之一；没有新信息时允许什么都不研究，而不是为了日报继续烧 token。

失败收敛参考现有 guard，但不能只看“收益没提高”或同类异常次数。建议冻结条件包括：同一证据集合重复提出同一实验、预先批准的诊断已完成且无新证据、边际信息增益低于事先定义标准、关键假设被反证、预算耗尽。终止的是本轮研究；新数据或 owner 明确改变问题时才创建有谱系的新轮次，不复活旧终态进行无限追逐。[K18]

**审批中心按真实对象建设。** 一般研究、既定预算内重跑、已配置能力内 testnet 行动不必机械地每步审批；这保留 owner 的宽自主边界。高预算／新增权限可以用明确设置或单个授权对象处理。只有真实需求足够集中时才建审批中心，不为原路线图强行制造审批项目。实盘始终独立人工闸门。

testnet 自主能力可在此阶段按明确范围启用，而非原则上禁止到阶段 3；但必须先具备持久化订单意图、稳定幂等键、未知结果核对、金额／持仓上限、停止机制和审计。该授权不代表已实现持续执行产品，更不代表试验收益可外推。

阶段 2 的价值验收是：owner 回来时能看到“新发现了什么、没有继续做什么及原因、花了多少预算”，而不是只看到 Agent 在线。冻结方向、没有新信息时保持安静，也是成功行为。

#### 阶段 3：冻结规则的前向观察，与 testnet 执行验证分开

观察对象是已冻结的策略修订、成本假设、风险阈值、观察区间与退出条件。改变规则必须另建修订，不允许把回看数据后改过的版本继续叫作原样本外观察。

经济证据与执行证据分别记录：前者来自事先约定规则下的市场数据和成本假设；后者来自真实 testnet 的订单／成交／持仓／对账。mock、dry-run 和 testnet 各自有清晰标签。testnet 成交只能证明相应环境的执行链路，不能被当作主网流动性、真实滑点或盈利能力的替代证据。

现有 `start_paper_run` 是单次流程。升级前必须采用“先持久化意图→发送→记录确认→查询／对账→归档结果”的路径；超时进入 unknown/reconciling，不能当失败立即再发。未取得 fill 不能等同于成交完成；部分成交、拒单、撤单、残余持仓、断网恢复、数量精度和账户限制都要有状态及测试。Binance 官方也明确区分 503 的未知执行结果和确定失败，并要求先查询避免重复；异常分类不能只看 HTTP 状态码。[K21][M18]

停止新下单、撤销挂单和关闭既有持仓是三种行为，必须分别定义。观察建议由证据阈值与异常触发，不能仅靠“连续运行了 30 天”自动晋升。最低样本、允许回撤和市场覆盖由评估协议事先约定；达到日历天数不是自动获得实盘权限。

#### 阶段 4：小范围实盘授权，不是切换一个环境变量

阶段 4 不承诺版本日期。只有前向观察、执行恢复、风控与审计达到门槛，才提交 owner 决策。实盘授权必须绑定具体策略修订、账户／场所、币种、仓位与杠杆限制、有效期和撤销机制；普通对话的“继续”“这个可以”不能被推断为授权。

研究建议、确定性风控判断和实际订单路由分层。授权后仍保留额度校验、对账、异常熔断、停止与风险降低政策；崩溃后的未知订单只能核对，不能自动重复。小资金试运行是风险控制方式，不是收益保证。若执行模型的复杂度已超出现有单策略适配能力，再根据真实需求评估 NautilusTrader 等内核，不预先建设多交易所平台。

### 10.3 工作量判断与资源安排

**这不是“加一个 handler＋一个卡片”的版本。** 以下是用于比较与资源决策的工程人日估计，非交付时间承诺；本次没有实施原型，估计可信度中低。假设一个熟悉 Python 的主开发者可获得前端协作，限定单策略、单用户与三币种，不做任意代码生成或订单簿仿真。

| 持久任务与对话运行时 | 6–10 | 队列、预算、取消、恢复、工具、模型问答及修订关联 |
| Web 主流程与启动打包 | 6–10 | 对话、卡片、比较、进度、设置、历史和目标环境启动 |
| 跨层故障、性能、安全与 owner 试用修正 | 5–8 | 不重复计各模块单测；覆盖完整路径和真实体验 |
| **合计** | **40–68** | 实际经过 M0 后重估；并行不意味着工作量消失 |

若选择扩展现有回测库，用 §3.3 的 12–22 人日替换引擎工作包，而不是把两条路径相加。若选择 LangGraph，原型和迁移的增减必须更新这张表；不允许在预算外“顺手引入”。完整经典 R-breaker 若需目前不存在的复杂 intrabar／订单规则，必须相应重估，不能偷偷降低 fidelity 来守住估计。

主要不确定性依次是策略定义、引擎语义适配、owner 启动环境和 Web 体验返工。AI 开发四个月留下多少代码，不等于剩余工作就少；AI 生成速度也不能替代金融正确性和真实验收。M0 后应给出实测依据与精简后的任务清单，继续优先削减非必要界面和平台工作，而非削减证据门槛。

### 10.4 从本稿进入开工的动作

owner 先裁决附录 B 的 P0 项；据此冻结 StrategySpec、VerdictPolicy、支持范围、预算与主界面。随后建立 ADR／OpenSpec 的 proposal、design、tasks、specs，将本规划的验收条件逐项映射到测试和任务，再更新 TODO／PROJECT_STATUS／ROADMAP，完成版本规划门后另行授权开工。

开发过程中若遇到需要第二个策略、常驻研究、审批中心、执行系统或全站重构的需求，先证明它是当前验收的必要条件；否则进入后续路线，而不是无限扩展 v0.5.0。
